# NFO 媒体库扫描优化调研

日期：2026-09-30。范围：`nfo_movie` / `nfo_tv` 的本地扫描。
本轮仅检查源码、规范和既有测试；没有改动业务代码、运行服务或执行生产扫描。

## 已确认的执行链路

`scanLocalLibraryFiles → ingestFile → ingestNFOMedia → buildLocalScanMedia → readNFOIngest → prepareLocalAsset → FindByPath → NFORepository.Ingest`。

- `scanner_local_ingest.go:22` 在普通文件的未变检测及批次传递之前分流 NFO。
- `nfo_local_ingest.go:218` 构造媒体时没有传入现有 `writeBatch`，因此每文件仍加载识别配置。`recognition_words.go:135` 包含表存在性检查及五项设置读取；启用时还解析规则。
- `nfo_local_ingest.go:97,107,142` 为每集读取整剧、单集和季资料。同一作品共享的 NFO 没有在这个流程内复用。
- `local_metadata_artwork.go:133,193,211,262` 按候选名称及扩展名逐项检查文件、兜底枚举目录，并检查海报尺寸。
- `artwork_store.go:104,203` 每个图片输入重新读取源文件、校验内容及尺寸、计算内容哈希。`artwork_store.go:231` 已有资产文件且大小相同时跳过写入，因此不应声称同图每次都重新落盘。
- `image_proxy.go:84` 的允许图片根目录已经有 30 秒缓存，不能误判为每张图片都查媒体库根目录数据库。
- `nfo_local_ingest.go:242` 的事务外 `FindByPath` 用来区分统计新增和更新。`nfo_repository.go:81` 在事务内再次查询并锁定同一路径。
- `nfo_repository.go:90` 才判断文件事实、状态、根目录、相对路径和绑定 fingerprint 是否一致。未变仍进入逐文件事务，获取 advisory lock，读库类型，读/锁媒体，读绑定；此时此前的 XML 和图片处理已经完成。
- 变化文件还调用通用私有 upsert，再查一次路径（`media_repository_upsert.go:169`）；图片各执行冲突插入和按哈希读取，条目逐层执行冲突插入及读取（`nfo_repository.go:112,132`）。剧集新增时整剧和季条目可能随每集重复 upsert。
- 全库及单根扫描当前都加载 `existingLocalMediaSnapshot`（`scanner_scan.go:86,181`），但 NFO 分支不使用它做未变判断；存在额外启动读取和内存占用。

以上证明存在重复工作，尚不能证明各项在当前 NFO 库的耗时占比。

## 候选方案及优先级

| 方案 | 主要收益场景 | 风险与约束 |
| --- | --- | --- |
| 接入现有识别规则批次复用 | 首扫、重扫，电影及电视剧均适用 | 风险较低；沿用每 100 次构造重新加载规则，保留 watcher 单文件即时读取。单根 1000 文件的五项设置读取可由 5000 次减至 50 次，这是操作次数推导，不是墙钟提速倍数。 |
| 减少冗余数据库读取及无用扫描快照 | 文件数量大；首扫和重扫均适用 | 将统计所需新增/已有判定从入库事务返回，省掉事务外路径查询；变化路径可复用已锁定行。保留事务内归属检查、首次入库锁和冲突重验。NFO 若不使用旧快照，可跳过其加载；若做后续增量优化，应改为读取真正需要的状态。 |
| 有界复用共享 NFO、图片和目录候选信息 | 同剧多集、同电影多版本；首扫和重扫均适用 | 收益潜力较大，但失效设计必须先明确。每次检查文件版本变化后复用解析及图片准备结果；保留候选优先顺序，检测同路径覆盖、新增候选、删除及错误恢复。缓存不能只有路径，也不能无界跨扫描保留。 |
| 将未变判断提前，形成 NFO 专用增量扫描 | 大多数文件已入库的反复扫描 | 收益潜力较大，风险也更高；必须跟踪视频、单集/整剧/季 NFO、图片及候选变化。当前没有覆盖这些输入的持久化文件事实快照，需要设计及迁移。仅凭视频 size/mtime 跳过会漏掉侧车更新；watcher 不能单独承担全量扫描的补漏职责。 |
| 降低整剧/季条目的重复数据库更新 | 首次大量导入剧集，或共享父资料变化 | 应先测事务耗时；可考虑相同字段时不执行冲突 UPDATE，或受控复用父身份。不能跳过父资料更新或合并成一个长事务来破坏逐文件失败隔离。 |

共享文件复用的例子：50 集都引用同一整剧海报时，仅该层海报输入就可能触发 50 次源文件读取及哈希；在文件版本未变的缓存窗口内可复用一次准备结果。实际收益受页缓存、目录结构、图片大小和数据库等待影响。

## 不可省略的正确性边界

- 仅路径或 `(size, mtime)` 不能完整识别文件覆盖。设计需考虑文件身份、更改时间、读前后校验及必要时内容复核；严格内容检查与减少磁盘读取之间的取舍不能隐瞒。
- 不缓存已经被仓储事务修改的输入对象。`NFORepository.Ingest` 会修改条目、父身份及 Asset ID；fingerprint 又序列化完整 input（`nfo_local_ingest.go:172`）。直接复用可变指针可能改变 fingerprint，导致本应跳过的文件重新入库。缓存应保存独立准备结果，并为每次入库复制所需对象。
- 保留逐文件事务、路径锁、来源/媒体库隔离；取消或单文件失败不能回滚已成功文件。
- 保留每文件独立绑定和版本身份、用户状态、首次创建时间。
- 无效/缺失 NFO 不清空已接受资料；缺图保留已接受资产；图片路径校验和大小限制不能被缓存旁路。
- 暂不推荐直接增加大并发或大事务。在本地机械盘场景，需要先确认 CPU、磁盘访问和数据库等待比例，才能判断是否值得并行。

## 后续验证建议

1. 同一套隔离数据分别测首次扫描、完全不变重扫、修改单集 NFO、修改整剧/季 NFO、覆盖共享海报、删除/恢复资料与图片。
2. 记录总耗时以及 XML、图片准备、数据库阶段耗时；同时统计设置读取、源图片读取字节、SQL 次数和事务次数。使用多次测量，区分冷/热缓存。
3. 既有 `TestNFOFreshStartupAndScan` 覆盖未变重扫、图片 watcher 更新和缺图保留；`TestNFORepositoryPreservesFilesAndPreviousSnapshot` 覆盖侧车变更、坏 NFO 保留及隔离。这些用例验证功能，不证明性能。本轮只阅读，没有重新运行。
4. 后续实现时补操作计数及文件覆盖/缓存失效的回归，保留取消、并发首次入库和失败后恢复的检查。

建议先实施规则复用与冗余读取削减，再在上述正确性边界内评估共享资料/图片复用；重扫仍慢时，再设计持久化侧车变更快照。当前没有 NFO 库生产性能样本，不承诺整库提速倍数。
