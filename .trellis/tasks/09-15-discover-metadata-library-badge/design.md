# 发现详情与入库标记设计

## 边界与数据流

保留 DiscoverDetailModal；打开 TMDb 条目时按 ID 和类型调用安全详情接口，复用 TMDbProvider 的电影/电视剧详情获取与现有图片代理。GET 响应只投影展示字段和演职员，不返回原始快照或凭据、不写入媒体；管理员本地命中后由弹窗异步调用独立刷新接口，复用媒体详情页的 canonical TMDb 刷新逻辑。元数据标签、语言地区本地化与演职员布局优先复用现有组件/函数，不将媒体专属管理操作带入发现弹窗。

列表入库状态单独批量查询，输入限定数量的类型/来源 ID，输出各作品的布尔状态。复用既有媒体可见性过滤及权威元数据标识，电视剧沿 episode→series 归属判断；有一个可见媒体即可，不统计完整度。查询失败不能伪装成确定未入库。

源发现缓存保持现有共享协议，不能写入用户相关入库状态。浏览器在账户/播放配置变化后撤销旧请求并重查；从本地列表缓存恢复也应重新查询入库状态。详情请求关闭时取消，不预取每张卡片详情。

## 字段与兼容

明确区分电影时长与电视剧来源提供的单集时长；来源未提供时显示暂无。豆瓣链接只读取已存在的可靠关联，不新增模糊匹配。新详情 DTO 的数组字段与列表的 Partial<Media> 字符串字段不能混用，须显式类型适配。

不改变发现 feed 分页/缓存/图片 URL，不修改数据库结构或红果下载改动。新增路由沿用 can_view_discover 权限。提取演职员纯展示部分时保持媒体详情原有请求与展示行为。

## 风险与回滚

真实 TMDb 网络可用性和缺失字段需分别报告；模拟测试不能代替真实来源验收。身份匹配、媒体可见性和共享缓存隔离是关键风险。回滚只移除新增详情/状态接口和展示，不删除任何媒体或元数据。

## 修订方案（优先于上述直接请求 Provider 的设计，待确认）

最新已确认修正：删除详情服务的 MediaVisibility 参数及 FindDiscoverLibraryItems 调用，以 FindByIdentifier 的 TMDb ID＋kind 命中本地 metadata 为唯一读取前提；列表状态接口保持原权限过滤。共享目录资料与媒体文件授权不是同一边界，不向预览返回路径或播放目标。

详情接口以精确作品身份读取共享 metadata，再读取整部电影/整剧的权威元数据、选定图片和演职员；演职员沿用 ListCreditsWithPeople 的 Person.Name 和 Role，不再以 Provider 的 OriginalRole 替换翻译。普通 GET 命中本地后不联网覆盖已有字段，缺项按详情页缺省语义展示；管理员随后可异步刷新最新资料，刷新沿用现有字段保留、图片/快照替换和译文保留规则。无本地 metadata 时使用原 TMDb 预览分支。保持安全 DTO、no-store 和媒体路径隔离；列表入库标签仍独立按可见媒体判断。

从 MediaDetailMetadata 局部提取双方实际共用的纯展示块，保留详情页原有数据加载、管理操作及媒体专属行。发现弹窗用同样的徽章、简介与标签布局，不伪造 Media 文件对象。背景使用现有 imageURL 和主题色渐变，保留海报，去掉重复 backdrop 缩略图。

预期修改仅限 discover 详情服务/handler、必要的可见性查询复用、相应测试、DiscoverDetailModal/Sections、MediaDetailMetadata 的共享展示部分及浏览器脚本。风险重点是本地时长与整剧时长口径、用户可见性、原详情页提取后的行为一致性。
