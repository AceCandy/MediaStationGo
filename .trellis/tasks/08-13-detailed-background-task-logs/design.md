# 后台任务详细日志设计

## Boundary

任务追踪与日志读取链路保持不变。各业务执行器在已有 `StartTriggered`、`Update`、`Finish` 调用中提供可读的 `Details`；`TaskTrackerService` 继续负责逐行落盘。

## Data Flow

1. 执行器完成一个人物、媒体、目录条目或媒体库工作单元。
2. 执行器从已有业务结果构造一条或少量中文明细。
3. 运行中的批量任务通过 `Update` 立即写入本批明细；单项任务通过 `Finish` 写入结果明细。
4. 任务中心沿用现有日志 API 展示 `[DETAIL]` 行。

## Decisions

- 人物翻译的窗口函数返回本窗口结果明细，避免任务层再次查询数据库。每个去重后的翻译组只记录一次，格式包含对象类型、原文、译文和来源。
- 人物补齐沿用现有结果回调，在成功与非法 ID 分支补足明细；保留现有错误和 404 失效说明。
- 媒体刮削在处理结束后读取已有媒体匹配状态/标识，生成一条结果明细，不改变刮削算法。
- 发现目录任务使用 job 的 provider/type/external ID，并在成功后读取已持久化 metadata 标题；失败使用已安全化错误。
- 全库扫描每处理一库调用一次 `Update`，输出该库计数或错误。最终 `Finish` 只保留汇总，避免重复全部明细。
- 回收站清理是单工作单元，在 `Finish` 中记录截止时间和删除数。
- 整理和轨道回填已有有界明细，不做无关重构。

## Compatibility And Risk

- 不改变公开结构、API 或数据库，旧日志仍兼容。
- 人物名称和媒体标题是管理员已可见的媒体元数据，按用户要求写入管理员任务日志；不写 provider 原始响应和 AI 上下文。
- 批量明细会增加日志体积。沿用日志读取 1 MiB 上限，并对累积型 `Details` 保持现有采样上限；逐批 `Update` 只传当前批新增行，避免重复写入。
- 回滚只需撤销执行器新增的 `Details` 和相应测试。
