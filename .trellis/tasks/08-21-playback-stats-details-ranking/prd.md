# 播放统计明细与热榜

## Goal

让管理员在 Web 播放统计页同时看清具体播放记录和指定日、周的热门内容，回答“谁在什么时候播放了什么”和“当前哪些作品最热门”。

## Background

- 当前统计页只展示播放总次数及按日、周、月聚合的次数，不展示具体媒体。
- `playback_events` 已记录用户、会话、元数据、媒体版本、媒体库和播放时间，可作为明细及排行的统一数据源。
- 播放统计仅管理员可见；手动标记已看不产生播放事件，新增内容必须继续以真实播放事件为准。
- 既有决策是不新增图表依赖、消息队列或预聚合表。

## Requirements

### R1：统一筛选

- 保留现有日期、账户、媒体类型和媒体库筛选。
- 同一组筛选条件必须一致作用于总数、时间序列、播放明细和热榜。

### R2：播放明细

- 按播放时间倒序展示符合筛选条件的事件，每页 20 条。
- 每条展示作品海报与标题、播放账户、媒体库和播放时间。
- 电视剧明细精确展示剧名、季集号和单集标题。
- 当前媒体版本仍存在时，点击作品进入现有媒体详情页。
- 桌面端使用表格，移动端使用卡片列表。
- 不展示会话 ID、文件路径等诊断字段。

### R3：每日/每周热榜

- 提供“每日 / 每周”切换和日期选择，一次展示一个周期，默认定位到当前筛选范围内最新周期。
- 电影按作品聚合；电视剧按季聚合，同一季的不同单集和媒体版本合并统计。
- 每期展示 Top 10，至少包含名次、海报、作品或剧名与季号、播放次数。
- 周统计沿用 PostgreSQL `DATE_TRUNC('week', ...)` 的周一开始口径和现有服务端本地时区。

### R4：状态与兼容性

- 明细和热榜分别提供加载中、无数据和加载失败反馈。
- 当前媒体文件已删除但共享元数据仍保留时，既有事件仍计入统计；明细显示不可用状态且不生成失效链接。
- 复用现有播放事件、媒体展示投影和 UI 样式，不新增数据库表、迁移、前端图表依赖或统计后台任务。

## Acceptance Criteria

- [x] 管理员能在播放统计页看到符合筛选条件的明细，字段、倒序和每页 20 条分页符合 R2。
- [x] 管理员能切换每日/每周并选择周期；默认周期及 Top 10 展示符合 R3。
- [x] 电影不同版本合并到同一作品，电视剧同一季的不同单集合并到同一榜项。
- [x] 日期、账户、媒体类型和媒体库筛选一致影响总数、时间序列、明细与热榜。
- [x] 媒体文件删除但共享元数据保留时，既有事件不从计数中消失，页面不会生成失效详情链接。
- [x] 加载、空数据和失败状态明确；桌面与移动布局无不可用横向溢出。
- [x] 非管理员访问仍由现有管理员路由和中间件拒绝。
- [x] 未新增图表依赖、消息队列、预聚合表或无关配置。

## Out of Scope

- 播放门槛、事件去重、观看历史、播放 Profile 隔离和权限规则调整。
- 单集热榜、媒体文件版本热榜、会话诊断、文件路径展示和报表导出。
- 实时榜单推送、离线预聚合及历史事件回填。
- 已异常删除共享元数据的孤儿事件按媒体类型恢复归类；现有事件没有保存媒体类型快照。

## Technical Notes

- `PlaybackEvent` 已保存 `metadata_id`、`media_id`、`library_id`、`user_id` 和 `played_at`，无需迁移。
- 作品展示可复用现有元数据/`MediaView` 的标题、剧名、季集号和海报投影。
- 前端可复用现有响应式媒体样式，以及播放器日志页的桌面表格/移动卡片分页模式。
- 查询必须继续在 PostgreSQL 中筛选、聚合和分页，禁止将全部事件加载到内存。
