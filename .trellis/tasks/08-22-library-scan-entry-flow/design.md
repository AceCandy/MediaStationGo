# 调整媒体库扫描入口与自动触发：技术设计

## 1. 边界

本次只调整扫描的触发入口和目标范围，不改变 `ScannerService` 的文件遍历、入库、删除缺失媒体、轨道探测或自动刮削行为。

## 2. 数据流

### 2.1 任务中心手动扫描

```text
TasksPage 选择一个媒体库
  -> POST /api/tasks/definitions/library_scan/run { library_id }
  -> Handler 校验 library_id 与媒体库存在性
  -> SchedulerService 携带单库目标异步运行 library_scan
  -> jobScanLibraries 只调用 ScannerService.ScanLibrary(目标库)
  -> TaskExecution 记录手动扫描进度与结果
```

`library_id` 对手动任务中心入口为必填。定时执行不携带该参数，继续遍历全部已启用媒体库。

### 2.2 保存后自动扫描

```text
真正创建新媒体库
  -> 保存成功
  -> 创建 trigger=event 的整库扫描任务
  -> 后台扫描新库全部启用路径

向已有媒体库新增启用路径
  -> 保存成功
  -> 创建 trigger=event 的单路径扫描任务
  -> 后台只扫描新增路径
```

新建媒体库服务返回“是否真正创建”和“本次新增路径”结果，避免同名同类型请求合并到已有库时误扫整个已有库。新增但禁用的路径不启动扫描。

## 3. 后端契约

- `POST /api/tasks/definitions/library_scan/run`
  - 请求：`{ "library_id": "<uuid>" }`
  - 空值或无效 JSON：`400`
  - 媒体库不存在：`404`
  - scheduler 正在运行：`409`
  - 成功排队：`202`
- 任务中心手动扫描继续使用 scheduler 的单任务并发保护，任务触发类型为 `manual`。
- 定时扫描不带目标，任务触发类型为 `scheduled`，范围保持全部已启用媒体库。
- 保存后扫描使用现有扫描任务追踪，触发类型为 `event`；任务必须先持久化，再启动后台扫描。
- 自动扫描启动失败只写服务日志，不改变已成功的保存响应，也不回滚数据。
- 现有 `/libraries/:id/scan` 与 `/libraries/:id/roots/:root_id/scan` API 保留，避免破坏外部调用兼容性。

## 4. 前端行为

- “媒体库扫描”任务行显示单选媒体库下拉框，默认未选择；未选择时不能运行。
- 不提供“全部媒体库”手动选项，也不提供多选或路径选择。
- 删除媒体库管理弹窗的整库扫描和路径扫描按钮及其无用回调。
- 删除媒体库详情页“立即扫描”、扫描进度状态和失去调用方的扫描状态 Hook。
- 新建媒体库和新增路径仍只展示原有保存成功反馈；自动扫描不新增 Toast。

## 5. 兼容性与风险

- 定时扫描复用原有 `jobScanLibraries`，仅在上下文明确携带手动目标时缩小范围。
- 任务定义仍使用稳定键 `library_scan` 和 `TaskKindScan`，历史记录与日志文件不迁移。
- 自动扫描与已有手动扫描可能同时到达；继续复用 `TryBeginLocalScan` 的现有进程内去重语义，不新增分布式锁。
- 删除 UI 入口后，底层扫描 API 仍保留，回滚 UI 时无需恢复后端路由。

## 6. 验证重点

- 手动任务缺少、错误或不存在的 `library_id` 被入口拒绝。
- 选择媒体库 A 不扫描媒体库 B；定时执行仍扫描 A、B。
- 真正新建媒体库产生整库 event 任务；新增路径只产生该路径 event 任务。
- 编辑已有配置不产生扫描任务。
- 所有扫描入口删除后前端无孤立 import、prop、hook。
