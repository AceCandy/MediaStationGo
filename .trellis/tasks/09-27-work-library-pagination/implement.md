## Bug Analysis: 作品优先查询仍被错误计划放大

### 1. Root Cause Category

D（测试覆盖缺口）与 E（隐式假设）：小 LIMIT 不代表少扫描；计算后的 kind 不能保留原列统计；精确 count 在密集库与空目录需要不同执行策略。

### 2. Why Fixes Failed

前轮用例没有显式 Series 的合集连接工作量断言；Latest 已有时间偏斜数据，但只按固定别名检查小库，漏掉真正候选；Series count 只验证稀疏目录。此次曾使用别名前缀检查，但子查询自动改名且分集资格也用相似别名，因此改为 CTE work_batch 子树累计访问量并断言至少检查到一个节点。仅增加 OFFSET 0 的初版仍被 OR 归属条件带回全表扫描，最终采用已知/未知互斥分支。

### 3. Prevention Mechanisms

P0：保留实际 SQL/绑定参数与计划检查，覆盖真实类型、候选子树、累计访问量、合集比较量、密集与稀疏分布；既有边界不放宽。P0：原查询 oracle 比较完整 ID、顺序、总数与状态；修前普通候选和密集 count 断言均失败，修后通过。

### 4. Systematic Expansion

共享红果 scope 的库内/全局消费者同时修复；普通 Items/Latest 的作品排序范围复用 helper，Latest 剧集预筛保留原 kind 与文件资格。没有扩大到后台扫描、图片或缓存。

### 5. Knowledge Capture

已同步 work-level-queries.md、prd.md、design.md；明确原生类型统计、限库先筛后排、互斥计数与按 CTE 子树而非别名检查计划。无新持久字段、依赖或后台服务。
