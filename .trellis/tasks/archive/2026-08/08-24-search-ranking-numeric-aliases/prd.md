# 完善搜索匹配与排序

## Goal

让 Web 与 Emby 的 Metadata 搜索使用一致、可解释的匹配与排序规则：避免中文
单字 OR 造成无关结果，支持 0–100 阿拉伯数字与标准中文数字双向命中，并对
OpenSearch 或 PostgreSQL 召回的最多 100 个候选，在 Go 中统一按匹配层级、
相关度、标题编号和年份排序后内存分页。

## Background

- 当前 OpenSearch 使用默认 `text` analyzer 和 `best_fields`，未指定
  `operator`；搜索“死神”会按单字 OR 命中“出生死线”“神墓”等无关标题。
- PostgreSQL 回退使用字面量 `LIKE`，不会产生相同结果，两个后端语义不一致。
- 当前 OpenSearch 依赖默认相关度顺序，PostgreSQL 只区分完全匹配、前缀匹配和
  创建时间；尚未实现统一的匹配层级、自然编号和年份排序。
- 用户确认非空搜索只保留最多 100 个候选，可接受第 101 条以后不展示、也不参与
  全局排序；因此两个后端不再按请求页码截取，由 Go 对候选全集统一排序和切页。

## Requirements

- R1：Web 与 Emby 继续共享 Metadata 候选搜索；Web 保持标题、原名、简介和类型
  字段范围，Emby 保持仅标题和原名，不改变路由、请求参数或响应结构。
- R2：关键词继续按现有空白、标点和符号规则清理、拆分、忽略大小写去重；多个
  关键词必须全部命中。每个数字等价候选只在所属关键词内 OR，不放宽关键词间
  的 AND 关系。
- R3：中文全文的“其它匹配”必须要求查询词分析后的全部 token 命中，不能再以
  单字 OR 返回只含“死”或只含“神”的标题。共享 token 规则将连续拉丁字母或
  数字作为一个 token，将每个汉字作为一个 token；同一关键词的一种写法要求
  全部 token 在同一字段命中，不同关键词可命中不同字段。标准数字及其等价写法
  作为不可拆分的完整 token，避免 `44` 错误命中“四十”。
- R4：匹配结果分为三个严格层级，层级优先级不可被相关度、编号或年份反转：
  1. 完全匹配：标题或原名等于完整查询或其数字等价写法。
  2. 完整包含：同一个标题或原名以查询顺序连续包含每个清理后的关键词或其数字
     等价写法，但字段不等于完整查询。
  3. 其它匹配：每个关键词均有一种写法的全部 token 在某个允许字段命中，但不
     满足前两个层级；不同关键词允许分布在不同字段。
- R5：完全匹配层内，同名或数字等价名称优先年份更高的作品，再以 Metadata ID
  升序稳定排序。
- R6：完整包含和其它匹配层内，依次按共享搜索相关度、标题编号降序、年份降序、
  Metadata ID 升序稳定排序；较低层级即使相关度或年份更高也不得越级。共享
  相关度按唯一 token 在标题、原名、`genres`、简介中的命中数依次降序，再按
  标题优先的最佳命中位置、覆盖跨度依次升序；不直接混用 OpenSearch `_score`。
- R7：标题编号识别阿拉伯数字和标准中文数字 `零` 至 `一百`（含边界），两种
  写法使用相同数值排序；未识别到编号时按 `0` 处理。
- R8：查询数字在 `0` 至 `100`（含边界）且为无前导零的十进制整数时，同时匹配
  原始阿拉伯数字和标准中文数字；查询为标准中文数字时同时匹配对应阿拉伯数字。
  原查询始终保留，转换候选只作为同一关键词的 OR 等价项。标准写法唯一：`0`
  为“零”，`10` 为“十”，`11–19` 为“十X”，整十为“X十”，其它两位数为
  “X十X”，`100` 为“一百”；`一十` 等变体不转换。
- R9：非空搜索时 OpenSearch 与 PostgreSQL 均从 `offset=0` 召回最多 100 个
  Metadata 候选；Go 对候选执行同一排序契约后再按调用方的 `offset/limit`
  内存切页。不得先按请求页码从后端分页再做页内排序。
- R10：非空搜索的返回总数是排序后候选数，最大为 100；命中超过 100 时不展示
  其余结果，也不承诺其与已召回候选的全局顺序。无关键词浏览的数据库分页和
  总数不变。
- R11：权限、NSFW、媒体库范围、可播放资格、Movie/Series 类型、数据库复核和
  结果组装行为保持不变。
- R12：分页沿用现有边界：负 offset 归零，非正 limit 使用默认 50；offset 超过
  候选数时返回空页。Web 与 Emby 根据各自允许字段计算同一套相关度，Emby 不得
  使用 `genres` 或简介参与排序。

## Acceptance Criteria

- [ ] AC1：搜索“死神”时，“死神”和“死神：千年血战篇”可命中；“出生死线”
  与“神墓”不命中；满足全部 token 但不连续的标题只能进入“其它匹配”。
- [ ] AC2：完全匹配始终排在完整包含之前，完整包含始终排在其它匹配之前；低层级
  的更高相关度、更大编号或更新年份均不能越级。
- [ ] AC3：同为“死神”的多个作品按年份降序；年份相同后按 Metadata ID 稳定排序。
- [ ] AC4：同层且相关度相同时，`死神10`、`死神十`、`死神9`、`死神2` 按编号
  `10、10、9、2` 排序；同编号再按年份降序。
- [ ] AC5：相关度不同时，相关度高的 `死神2` 可以排在相关度低的 `新死神10`
  之前，编号不覆盖相关度。
- [ ] AC6：输入 `44` 可命中标题中的 `44` 与 `四十四`；输入 `四十四` 也可命中
  两种写法，并正确区分完全匹配与完整包含。
- [ ] AC7：数字转换覆盖 `0、1、9、10、11、20、44、99、100` 的双向结果；
  超出范围、带前导零或非标准中文数字不扩展，但原查询仍正常搜索。
- [ ] AC8：非空搜索无论调用方请求哪一页，后端请求固定从 0 召回最多 100 个
  候选；Go 先统一排序再切页。前后页在这 100 条候选内保持同一全局顺序，返回
  总数不超过 100。
- [ ] AC9：现有权限、类型、Metadata 去重、可播放复核、Emby 响应结构和 Web
  卡片行为不回退；定向 Go 测试及 `git diff --check` 通过。
- [ ] AC10：纯 Go 单元测试证明 OpenSearch 与 PostgreSQL 候选使用同一个排序器；
  `死神2` 可因共享相关度高于 `新死神10`，相关度相同时才按 `10 > 9 > 2`。
- [ ] AC11：多关键词允许分别命中不同字段而进入“其它匹配”，但“完整包含”必须
  在同一个标题或原名中按查询顺序连续包含；Emby 不使用简介或 `genres` 提升
  相关度。

## Out of Scope

- 不支持 `101` 以上数字、`007` 等前导零、`〇`、`两`、财务大写数字、罗马数字或
  年份特殊读法。
- 不引入 IK、同义词词典或新的第三方依赖。
- 不扩大 Emby 到 Season/Episode 搜索，也不改变无关键词浏览和播放逻辑。
- 不保证第 101 条以后命中的完整性、可见性或全局排序正确性。
- 不尝试复刻 OpenSearch BM25 分数；相关度使用项目内共享、确定性的轻量规则。
