## 目标

按响应实际需要读取页内作品的文件、分集、收藏与有效播放状态，移除没有被消费的字段和聚合，减少不必要的状态计算。复用现有查询，保持卡片内容、权限、分集去重及已看判定正确。

## 实施前已确认事实

- `internal/service/emby_hongguo_library.go:182`：分页之后调用 `hongGuoLibraryNodes`，再按分页得到的展示 ID 顺序组织响应。当前已经是页内批量查询，不是每部作品分别发送一条 SQL，也不是本项才引入先分页后补详情。
- 同文件 `:202`：页内查询读取源作品、文件绑定、Media、分集和有效播放状态，先按源作品统计，再补封面/收藏并合并展示卡片。合集可包含多个源作品，页内卡片数量不等于源作品数量。
- 同文件 `:214`、`:220`：查询计算代表文件 `MIN(m.id)` / `MIN(v.media_id)`、最后观看时间 `MAX(s.watched_at)` / `MAX(v.played_at)`、最大播放位置 `MAX(COALESCE(s.position_ms,0))` / `MAX(v.position_ms)`。
- `internal/service/emby_hongguo.go:388`、`:445`：纯 Series 卡片不使用上述代表文件 ID 和最后观看时间，播放位置直接返回 0；Movie/Episode 路径仍可能需要代表文件或播放位置，不能全局删除。
- `internal/repository/playback_state.go:33`：`PlaybackStates` 不只是读 completed，还可能在原文件不可用且有断点时定位替代版本、按片长推导完成状态。这些推导可能影响已看结果，不能一概称为无用计算。
- 同文件 `:89`：已有 `CompletedPlaybackStates`，明确完成的记录直接返回身份；未明确完成且有断点的记录复用有效状态推导，可作为只需要已看身份时的复用候选。
- 前次慢请求诊断中，红果约 2.14 秒请求的页内详情 SQL 约耗时 1.31 秒；这是整条 SQL 的历史耗时，不是上述三项聚合各自的耗时，也不能证明删除它们即可解决主要瓶颈。
- 普通库和 NFO 已纳入范围，但尚未完成逐路径字段消费审查；不能声称它们都有与红果完全相同的三项冗余。

## 需求与边界

1. 覆盖普通电影/电视剧、NFO 电影/电视剧、红果库的同类 Emby 页内详情与状态查询，并核对被调整的共享方法及其其他调用方。逐路径区分 Series、Season、Movie、Episode、混合类型与请求字段，识别实际消费的查询结果。
2. 移除已证明未被响应、代表版本选择、排序、过滤、身份映射或其他调用方使用的字段及相关聚合。红果纯 Series 路径至少核对并精简上述代表文件 ID、最后观看时间和播放位置三项；其他库的同类冗余一并处理，不机械照抄字段删除清单。
3. 只需要已看/未看结果时优先复用现有有效已看查询；只有确实需要完整进度、时长或时间字段的路径才读取对应完整状态。保留显式完成、取消已看、重播断点、旧文件删除后的替代版本、片长变化及多段文件规则，不直接用原始 completed 字段替换有效状态。
4. 保持作品到文件/分集的正确关联，按用户及各来源逻辑身份隔离收藏和历史；不能仅凭当前 Media ID 关联状态而丢失换版本后的历史。分集数量按实际合格分集去重，不能改成文件数量或资料库宣称的总集数。
5. 保留响应实际使用的集数、未看数量、是否完成、收藏、封面和日期；合集身份、成员范围、汇总方式与顺序不变。页内查询不重复承担第 2 项的筛选和计数工作，也不得在分页后丢弃本应返回的合格作品。
6. 使用当前页作品身份限定可安全限定的数据范围，避免重复读取；是否已有条件下推、是否仍扫描过多状态，以实际 SQL 和执行计划确认，不能仅从子查询写法断言全量扫描。
7. 与第 2 项确定的 NSFW 库级化和仅限 NFO 的 DateCreated 规则保持一致，但本项不另行改变权限、日期含义、已看规则或总数契约。复用现有方法，不默认新增缓存、汇总表、依赖或通用查询框架。
8. 先复测第 2 项完成后的候选与页内详情阶段，再确定剩余热点及本项收益；不预设详情仍耗时 1.31 秒，不把第 2 项收益重复计入本项。
