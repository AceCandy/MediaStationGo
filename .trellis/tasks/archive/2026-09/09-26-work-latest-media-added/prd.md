# 统一作品最新媒体入库时间

## 目标

普通、NFO、红果按作品维护最新现存 Media 入库时间，统一 Web/Emby 最近添加排序；历史仅一次性补算。追加持久库归属，减少最近添加候选反复从文件提取、去重作品身份的成本。后续将作品级候选作为共享读取规范，修复全局列表及同类消费者未沿用既有优化的问题。

## 已确认规则与事实

- 用户确认同一作品在 A/B 库共用全局时间，任一库新增 Media，两库均提前；可见性与排序时间分开。
- 字段 latest_media_added_at 为当前存在的关联 Media 的 MAX(created_at)，不是扫描/播出/资料更新时间。电影包含版本，剧包含季集，红果包含合集所有季。
- 删除最新文件后回退到剩余最大值，全删置空；重绑同时影响旧、新作品。DateCreated 保持原契约。
- 历史只补一次，不加入启动回填、定时任务或永久补算接口。
- 实测红果候选约 16.95 秒、页内详情约 1.95 秒，位于 internal/service/emby_hongguo_library.go:86,109。
- NFO 身份按库隔离（internal/model/nfo.go:9），本任务不合并不同身份。红果合集为关系投影而非实体表，代表取最小 season_index/source_id（internal/repository/hongguo_groups.go:14）。
- 库归属表示当前仍有文件的库集合，不代表用户权限。共享作品在 A/B 两库各展示一次；删除 A 的最后一个文件后只退出 A，B 保留。用户所说的新增字段位于作品/媒体项，不是物理 Media。
- R5 实施前的普通 Latest 从 Media 提取库成员（当时 internal/service/emby_metadata_scope.go:84,116）；前轮实际电影库有候选约 20→153 ms 的退化，原因与完整库成员读取有关，不能只验慢库。当时增量触发器不检测纯 library_id 更新（internal/database/latest_media_added.go:37）；这两项已由持久库归属阶段处理。

## 范围

R1：普通、NFO、红果作品维护持久字段及索引，红果合集取各成员季时间最大值，不按当前库文件限制该时间。
R2：覆盖 Media 新增、删除、时间/归属改变、绑定变更与层级调整，事务内维护；重复扫描和资料 Save 不覆盖派生值。
R3：Web/Emby 最近添加、DateLastContentAdded 使用新时间；保留权限、库成员资格、播放筛选、分页总数和合集代表。DateCreated、标题、上映时间排序不变。
R4：维护机制就绪后一次性补算现有数据并核对，只记录脱敏验证结论，不保留生产凭据或导出。
R5：普通作品（含季集祖先）、红果源作品持久维护当前库集合；NFO 复用已有 LibraryID。覆盖新增、删除某库最后一个文件、纯换库、重绑、移季、批量及级联变更，同一事务提交或回滚，不由资料刷新覆盖。
R6：持久库归属阶段先接入 Emby 指定库 Latest 与 Web 最近添加共享候选入口，替换纯库归属推导；该阶段不重写全局无库限制的查询、其他排序、搜索、详情及播放协议，后续读取扩展见 R10–R13。权限、有效状态和原候选资格仍在分页前检查，不能把库集合当作这些规则的替代。
R7：红果合集按当前关系联合成员库归属，保持跨库全局时间与无文件首季代表；不把合集归属存到任意代表季。NFO 不新增冗余多库数组。
R8：旧作品未初始化库归属时保持原可见性，不能误当无文件。新增历史库归属仅一次性运维补算，不放入启动/定时回填；本轮规划不授权生产写入、停写或重启，实际生产操作另行确认。
