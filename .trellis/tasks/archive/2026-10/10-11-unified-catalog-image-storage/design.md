# Unified catalog image storage

- Persist new artwork/person keys relative to DataDir as `catalogs/<source>/<category>/<hash[0:2]>/<hash[2:4]>/<hash[4:6]>/<hash><ext>`. Source identifiers are normalized and path-safe; local_nfo/manual map to local.
- Keep original-image SHA values, asset IDs and API URLs. Artwork identity becomes unique storage key plus matching content hash, replacing the global SHA uniqueness constraint. Multi-source historical artwork references split into source-specific assets; one original ID remains usable.
- Pass explicit source through every import, repair, catalog, NFO and avatar call path. Source-scoped avatar URL caches cannot return another source's key.
- Run idempotent, local-only migration before server listeners/background workers start. Copy and verify bytes before updating references; missing/corrupt sources retain their old reference for existing repair paths. Preserve old bytes for recovery instead of deleting shared originals during migration.
- Prefer filesystem reflink for originals and thumbnails, verify cloned bytes, and fall back to writing validated data when unsupported or changed. Preserve sync and atomic replacement; never hard-link source and destination.
- Batch artwork ownership/destination lookups and ordinary key updates in groups of 100. People/catalog/cover keys also commit per batch using observed-key comparisons. Flush pending ordinary updates before transactional asset splitting; reserve their destination keys within the batch. Keep image bytes out of batch plans.
- Cover legacy artwork references (selections, candidates, Douban and NFO), people keys including rich Douban JSON, Hongguo/Huangguo local keys and uploaded library cover URLs. Historical unowned assets use legacy. Libraries use content-addressed local artwork files; clearing one cover must not delete bytes shared by another library or local artwork.
- Catalog thumbnails live beside their original in `<hash>.thumbnails/v1/<spec>`. Their identity includes content hash, processing version and normalized options, independent of absolute path or mtime. Only validated catalog-shaped paths use this layout; proxy caches and user media-library originals retain their existing lifecycle.
- Legacy path readers remain compatible during partial migration. A separate pass over cache groups follows original migration, verifies matching original bytes, and copies the current legacy version beside the new original. Scan the existing catalog cache layout first, then pre-catalog layouts, without scanning all originals. This covers already-migrated originals even if the earliest old originals were removed. Existing target thumbnails and legacy files remain intact; missing variants regenerate naturally.
- This change requires schema and data compatibility tests; deployment on real data is separate from isolated test execution. No production restart, automatic commit or ad-hoc production writes during development.
