# TMDb 季集复查按播出时间分档

## Goal

减少老季缺资料目标的重复 TMDb 请求，让近期播出的季更及时获得季/集信息补全。

## Background Before This Change

- 现有任务仅处理有媒体且缺资料的季/集；资料完整的目标退出待办。入口见 `internal/service/tmdb_recheck_queue.go:153`。
- 成功但仍缺资料、HTTP 404 和整季清单未包含目标集，目前均采用 72 小时冷却，见 `internal/service/tmdb_recheck_queue.go:188`、`:221`、`:285`。
- 后台按季互斥领取，季内分页处理；当前按到期时间排序，见 `internal/repository/tmdb_recheck_season.go:13`。
- 季与集都有 `release_date`；季日期来自该季首播日期，不能单独代表该季最近更新，见 `internal/service/catalog_hydration.go:675`。整季响应包含各集的播出日期，见 `internal/service/tmdb_catalog.go:82`。
- 缺播出日期本身就是复查条件，见 `internal/repository/tmdb_recheck_queue.go:225`，因此未知日期必须有明确兜底。

## Requirements

- 按目标所属季判断新旧，同一剧的新季不能让其老季一同高频复查。
- 最近播出在一个月内的季冷却 1 天；超过一个月至一年冷却 10 天；超过一年冷却 20 天。
- 近期季在已到期待办中优先扫描；同档继续按到期时间处理。未到期目标不得因优先级被提前请求。
- 优先使用该季最近已播集的有效日期；缺少分集日期时再参考季日期。使用已有本地元数据与可信 TMDb 季数据，不为判断新旧增加单独网络请求。
- 成功但仍缺资料、404、整季清单缺集共用分档策略；日志所述等待时间应与实际到期时间一致。
- 保留资料完整退出、无媒体退出、身份异常阻塞、网络/保存错误退避、固定本轮截止时间及租约并发保护。
- 手动执行该维护任务也遵守冷却；原有显式元数据刷新行为保持不变。

## Acceptance Criteria

- [x] 覆盖三档和月/年边界，近期播出不会因首播时间较早而落入老季档。
- [x] 同剧新季与老季分别分档；同季的季/集目标使用一致的播出新旧依据。
- [x] 已到期近期季先于老季领取；冷却中或租约有效的目标不被抢占。
- [x] 成功仍缺资料、404、清单缺集的到期时间与日志一致；资料齐全后不周期性重刷。
- [x] 未知/非法日期与待播数据按最终确认的兜底规则处理。
- [x] 既有冷却目标切换策略时有明确生效规则，不重置运行租约或普通失败退避。
- [x] PostgreSQL 定向回归验证调度与并发，并检查大队列领取计划，避免每领取一季都对全部季集重新聚合排序。
- [x] 独立复核代码差异与现有调用方；未运行的验证明确列出。

## Out of Scope

- 不扩大为资料已齐全对象的周期性全量刷新。
- 不新增配置面板、调度任务或自动文件清理。

## Confirmed Decisions

- 用户已确认：无有效播出日期的目标保留 3 天冷却。
- 月、年按 30、365 天计算，以 UTC 播出日判断；未来 30 天内有播出安排也进入近期档。
- 已保存的到期时间不批量重置；到期核对及后续结果保存使用新规则。
