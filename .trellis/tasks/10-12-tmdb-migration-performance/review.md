# 实现、验证与剩余限制

## 根因
生产只读查询确认 tmdb_payloads 每次 INSERT 触发 tmdb_catalog_source_changed。原查询对 metadata_identifiers.external_id 做 CASE/正则/数值转换，唯一索引只能用于 provider/entity_kind 前缀，一次过滤 416299 条无关标识，EXPLAIN ANALYZE 811.803ms。这类查询会被每个来源正文（含季派生的集正文）重复执行。

## 修复
仅改触发器身份查找：转换单个来源 tmdb_id 为文本，按现有唯一索引三个字段等值查找，继续保留原正整数1–10位匹配约束。无新增索引、配置、表、网络调用、并发或事务策略变更。现有启动 schema 迁移自动替换函数；未操作生产库或重启服务。

## 验证
- 在真实生产数据上仅执行 SELECT EXPLAIN ANALYZE，对照等值查询 3.371ms。两者含相同的最新来源定位子查询；这是单个查询样本，不代表整个迁移加速倍数。
- 隔离 PostgreSQL 30000 条同类标识、使用实际安装函数抽取的查询并强制 generic plan：旧实现先失败并扫描全部标识（23.533ms）；新实现命中 provider/entity_kind/external_id 完整唯一索引（0.030ms），不扫描无关标识。
- 触发器正确通知目标；不同provider/kind、前导零、非法ID不误通知；超长数字保持旧限制；人物正文不通知；事务回滚同步撤销通知；重复安装兼容。
- 独立只读复核未发现行为阻塞；按建议加强计划断言，同时校验三个字段及唯一索引名称。
- PostgreSQL database/repository/service 来源中心、启动与回填专项 go test -race 全通过（7.384s/21.991s/27.471s）；加强后的计划专项另行补跑。go vet ./internal/database 与 git diff --check 通过。

## 后续深入审查：发现待修复问题

隔离 PostgreSQL 受控交错测试确认：SaveResponse 预读人物后，另一个数据库连接通过 SavePersonImage 完成相同路径头像的落库；当前事务随后合并人物名字并执行整行 Save，将已经成功的 image_key/image_source_path/image_status 覆盖成预读的空值/pending。来源写入锁不覆盖 SavePersonImage，因此事务专属缓存不能保护这类并发。原整行写入也存在读写间隙，此轮预读和复用进一步延长了旧状态的存活时间。

复现结果：人物名称正确变更，但 image_key=""、image_status="pending"、image_source_path=""。之前 race 检查及事务间更新测试未覆盖数据库交错，上面的“未发现回归”仅是当时的静态审查结果，不能作为最终通过结论。

建议最小修复：现有人物更新只写来源资料列；profile_path 不变时不写图片下载列，路径变化时仅重置 image_status/image_retry_at，保留已有本地图片回退信息。新人物仍完整创建。需加入受控双连接回归，并检查路径变化与旧图片完成写入的顺序。

剩余性能候选：演职员关系按有限批次插入（仍在单份响应事务内）；持久化迁移阶段/游标并单独保留失败重试；人物种子按批读取已存在身份；维护任务按页预读主体/父级并批量插入。都需独立验证，尚无新的生产吞吐实测。本轮仅审查，未修复业务代码；复现临时测试文件和数据库已清理。
