# 统一任务执行列表技术设计

## 1. 边界

本次包含两个相互配合但职责分离的机制：

1. 任务执行记录：面向管理员展示一次后台执行的摘要、状态和日志。
2. 刮削待办调度：根据媒体或目录对象当前状态选择下一部电影或电视剧处理。

执行记录不作为业务队列，也不保存刮削断点。业务对象状态是唯一待办依据。

## 2. 任务执行记录

### 2.1 数据模型

新增 `TaskExecution` 模型并注册到 `model.AllModels()`：

- `id`：UUID 主键，同时作为日志文件名。
- `kind`：organize、scan、scrape、probe、people、recycle 等任务类型。
- `trigger`：manual、scheduled、event。
- `name`、`stage`、`message`：列表摘要。
- `status`：running、completed、failed、interrupted。
- `source_path`、`dest_path`：现有任务上下文。
- `metrics`：JSONB 指标快照。
- `error`：失败摘要。
- `started_at`、`updated_at`、`finished_at`：执行时间。

服务启动时将数据库遗留的 `running` 执行记录更新为 `interrupted`。该更新只修正展示状态，不重排业务工作。

### 2.2 TaskTrackerService

保留现有 `Start`、`Update`、`Finish` 调用形态，内部改为：

- `Start` 插入 `TaskExecution`，创建运行句柄并发布实时事件。
- `Update` 更新摘要字段和 metrics；详细文本追加到任务日志。
- `Finish` 写入终态、结束时间和错误摘要。
- `Snapshot/List` 从数据库按开始时间倒序分页，不再依赖内存 `recent`。

服务仍可保留很小的运行句柄映射用于进程内更新，但数据库是列表状态的权威来源。

### 2.3 任务日志

日志根目录为 `<data_dir>/task-logs/<YYYY-MM-DD>/<task-id>.log`。

- 每次写入按当前本地自然日选择文件；跨日自动换文件。
- 文件只追加 UTF-8 文本，每行带时间和级别，不从日志恢复状态。
- 以任务 ID 为锁粒度串行写入，文件权限沿用数据目录的私有权限约定。
- 详情接口只接受任务 ID，由服务端从任务开始日到结束日（运行中取今日）生成候选路径并顺序读取。
- 接口支持尾部读取上限，避免一次响应无界占用内存；首版不做全文搜索、轮转和自动清理。

## 3. 统一任务 API 与前端

管理接口：

- `GET /api/tasks?page=&page_size=`：返回统一执行记录分页结果。
- `GET /api/tasks/:id/log?tail_bytes=`：返回该任务按日拼接的日志内容及是否截断。
- 现有任务实时事件继续用于刷新运行状态；轮询作为恢复手段。

任务中心只渲染一张执行列表，支持触发来源、类型、状态、时间和摘要。点击记录打开日志详情。周期任务通过工具栏入口打开管理面板，继续使用现有 scheduler 状态和立即运行接口，不作为第二张执行记录表常驻。

## 4. 刮削待办与优先级

### 4.1 待办来源

高优先级：已入库媒体。

- 新增或需要重刮削的媒体以 `scrape_status` 为待处理依据。
- 显式重新触发时，将目标作品范围内媒体置为 `pending` 并清空 scrape error，然后唤醒 worker。
- 作品键优先使用电视剧系列身份；电影版本使用共享 metadata 身份；尚未匹配时使用稳定的本地系列身份或媒体 ID 回退。

低优先级：TMDB 发现目录。

- 继续使用 `CatalogHydrationJob` 和三个 hydration checkpoint。
- 显式重新触发已完成目录对象时，重置该电影或电视剧树的相关 checkpoint，并把已有 job 重置为 pending，而非依赖唯一键 `DoNothing`。

### 4.2 单 worker 调度

ScraperService 只启动一个统一刮削 worker：

1. 先 claim 一个已入库媒体作品单元。
2. 没有媒体待办时，再 claim 一个发现目录作品单元。
3. 完整处理当前电影或电视剧，中途不抢占。
4. 单元完成或失败后回到步骤 1，重新检查高优先级队列。

网络处理不放在数据库事务中。claim 使用短事务或条件更新防止同一对象重复领取；写入仍依赖现有幂等 upsert 和 checkpoint。

### 4.3 作品粒度

- 电影：该电影及共享同一 metadata 的媒体版本。
- 电视剧：系列根、全部季、全部集以及关联的已入库媒体。

当前 Catalog series 的 season-turn requeue 改为单次完成整部电视剧；内部仍逐步写 checkpoint。失败或重启后，下次处理同一电视剧时跳过已完成子项，但从任务中心看是一次新的执行。

当前整库媒体刮削抽取为“查询一个作品 + 处理一个作品”的内部能力；现有整库入口只负责批量重置目标范围并唤醒 worker，不再自己启动并发刮削 goroutine。

## 5. 其他任务接入

- 计划 `library_scan` 和 `recycle_purge` 在实际执行外围创建 TaskTracker 记录。
- `organize_source` 沿用 pipeline 已有记录，避免调度器重复创建。
- 扫描、手动刮削、轨道回填、人物回填继续沿用 TaskTracker 入口，并补充 trigger。
- 文件监听循环、ffprobe worker、通知和其他内部 goroutine 不创建任务执行记录。

## 6. 兼容、失败与回滚

- API 可在过渡期保留旧 `background_tasks` 响应字段，前端切换完成后再删除，避免一次提交内前后端耦合失败。
- 数据库写入失败时，任务启动应失败并记录应用日志，不能出现实际后台执行但任务中心完全无记录的静默分叉。
- 任务日志写入失败不阻断业务执行，但在任务摘要中记录日志不可用提示并写应用日志。
- 回滚前端不会删除任务表或日志；回滚后端前应保留新表，避免不可逆数据删除。

## 7. 验证重点

- TaskTracker 的开始、更新、终态、启动恢复与分页。
- 跨日任务日志的追加、顺序读取、尾部限制和路径安全。
- 重新触发将媒体或目录对象恢复为待处理。
- 统一 worker 串行、媒体优先、电影/电视剧不可抢占。
- 电视剧处理中到达媒体待办时，完整电视剧结束后下一单元切到媒体。
- 现有手动、计划和事件触发流程没有重复执行记录。
