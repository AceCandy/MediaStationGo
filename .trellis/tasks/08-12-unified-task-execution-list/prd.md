# 统一任务执行列表

## Goal

将任务中心的后台任务执行记录统一为一张列表，让管理员能在同一处查看手动、定时和事件触发任务的执行状态、进度与结果；调度周期配置继续作为独立能力，不与执行记录混淆。

## Background

- 当前任务中心同时展示 `TaskTrackerService` 的后台任务记录和 `SchedulerService` 的周期任务状态，两者是不同的数据模型。
- 后台任务记录目前仅覆盖显式调用任务追踪器的 `organize`、`probe`、`scan`、`scrape`、`people` 流程。
- 周期调度器当前注册 `library_scan`、`organize_source`、`recycle_purge`；其中并非每次执行都会产生后台任务记录。
- 用户已明确选择统一为一张“任务执行列表”，而不是把所有后台流程改造成可配置周期的定时任务。
- 现有应用日志支持 console 或 JSON 编码，且会按文件大小、备份数量和最大天数轮转；项目当前没有从应用日志重建、查询或分页任务状态的能力。
- 独立任务日志按“任务 + 自然日”分文件，只需追加写入与按任务 ID 读取，不承担状态查询、分页或事件归并，因此不复用通用 `app.log` 的复杂轮转读取逻辑。
- TMDB 发现目录抓取已经使用持久化 `CatalogHydrationJob` 队列，并在启动时把中断的 `running` 记录恢复为可重试状态。
- 扫描入库刮削与 TMDB 发现目录抓取共享底层 provider 元数据、图片和人物持久化能力，但前者需要从本地媒体识别匹配，后者已有 TMDB 标识，执行入口并不完全相同。

## Requirements

- 任务中心使用一张统一的任务执行列表展示纳入范围的后台执行记录。
- 纳入范围包括手动或定时触发的媒体库扫描与整理、手动刮削、轨道回填、人物回填，以及定时回收站清理。
- 统一列表至少区分任务类型、触发来源、执行状态、进度或阶段、开始时间、完成时间和失败原因。
- 触发来源至少区分手动、定时和事件触发。
- 同一业务执行只产生一条主记录，避免调度器记录与实际执行记录重复展示。
- 数据库保存任务摘要与当前状态，支持统一列表查询；任务详细过程写入按任务和自然日拆分的追加式日志文件。
- 日志采用日期目录与任务 ID 组成的服务端固定路径；任务跨日运行时写入新日期下的同任务日志文件。
- 任务详情根据任务记录的开始与结束日期，按时间顺序读取对应任务的每日文件；不要求跨任务全文检索，也不从日志归并或恢复任务状态。
- 任务日志路径由服务端根据日期和任务 ID 生成，不接受客户端文件路径。
- 任务记录与日志暂不自动清理，长期磁盘占用由部署方管理。
- 刮削待办以业务对象当前是否已完成刮削为准，不保存任务级执行断点，也不通过旧任务记录决定从哪里继续。
- 媒体库对象使用 `scrape_status` 作为待办依据；未刮削或出错对象可被 worker 再次选取。发现目录对象使用现有 hydration 完成标记作为待办依据。
- 任意对象可随时重新触发刮削；重新触发时将对应媒体状态或目录 hydration 标记重置为待处理，并唤醒 worker。
- 服务重启后，worker 直接继续扫描仍处于待处理状态的业务对象；新一次处理创建新的执行记录，旧记录不参与恢复。
- 扫描入库刮削和 TMDB 发现目录抓取使用同一个串行刮削调度器，不同时执行；扫描入库刮削优先于发现目录全量抓取。
- 刮削调度的最小执行单元是一部完整电影或一部完整电视剧；电视剧单元包含其季、集等目录补全工作。
- 新入库媒体到达时不打断正在处理的电影或电视剧；当前单元完成后重新检查高优先级媒体队列，优先队列清空后再继续发现目录抓取。
- 两类刮削保留各自适配其输入的执行入口，同时复用现有底层 provider 与持久化逻辑。
- 周期、启停和“立即运行”等调度配置不混入执行记录；其管理入口需保留。
- 不把普通同步请求、常驻服务循环或无独立用户价值的内部 goroutine 自动视为任务执行记录。

## Acceptance Criteria

- [ ] 管理员能在任务中心的一张列表中看到纳入范围内由手动、定时和事件触发的任务执行。
- [ ] 每条记录能明确识别触发来源，并展示该次运行的运行中、成功、失败或中断状态；这些状态不作为业务刮削断点。
- [ ] 运行中的任务继续展示现有阶段、消息和指标信息；完成后能查看完成时间或错误。
- [ ] `library_scan`、`organize_source`、`recycle_purge` 的实际执行不会因触发方式不同而遗漏或重复记录。
- [ ] 调度计划仍可查看状态并执行“立即运行”，但不作为另一张执行记录列表与统一列表并排竞争。
- [ ] 现有整理、扫描、刮削、轨道回填和人物回填任务的执行追踪不回退。
- [ ] 服务关闭或异常中断后，未成功消费的刮削触发点在下次启动时可重新执行，并产生新的执行记录。
- [ ] 扫描入库刮削存在待处理工作时，不启动新的 TMDB 发现目录抓取；两类刮削不会并发执行。
- [ ] 已刮削对象可随时重新触发；重置为待处理后再次进入队列，其中已入库媒体仍优先于发现目录对象。
- [ ] 发现目录处理一部电影或电视剧期间到达的新入库媒体不会中断当前对象；当前对象完成后，下一个执行对象来自高优先级媒体队列。

## Technical Notes

- 复用并扩展现有 `TaskTrackerService`，不并行维护第二套任务执行服务。
- 发现目录抓取保留 `CatalogHydrationJob` 与 metadata/artwork/catalog checkpoints；这些业务标记负责幂等和重启恢复，任务执行记录不负责断点。
- 当前发现目录 series job 按 season turn 主动 requeue，实施时需改为单次执行完整电视剧；失败或重启后仍可利用已写入的子项 checkpoint 跳过完成部分。
- 当前媒体库刮削批量处理整库，实施时需抽取一个电影或电视剧作品单元的处理入口，统一调度器每次只选择一个作品。
- 周期任务管理从任务中心的独立入口打开，不再以第二张列表常驻在统一执行列表下方。

## Out of Scope

- 将所有任务都改造成可配置的周期任务。
- 将普通 HTTP 请求或常驻后台服务的每次内部活动记录为任务。
- 新增任务取消、暂停、重试或优先级能力，除非后续明确要求。
- 文件监听器、媒体探测内部工作队列、目录补水与人物翻译常驻 worker、通知发送等内部执行细节。
